## 截图和链接如何搭配

用户页先给 3～5 步可直接操作的文字，再在容易找错的位置放真实截图。优先覆盖“选择空间/保存到”“文件卡片/右侧预览”“逐项确认”三个场景；当前已提供预览截图，其余在对应界面稳定并实测后补充。

截图存放 docs/assets，使用描述性文件名和替代文字，旁边注明采集日期、适用界面和必要的版本差异。只使用测试账号、示例文件；截图前隐藏地址栏中的 token、账号资料及真实业务内容。不要用生成图模拟真实操作界面。界面位置变化才重拍，普通文案修订优先更新文字，避免每个按钮都堆截图。

截图帮助识别位置，不能替代可复制、可检索的步骤。链接放在相关步骤后，使用“查看原文”“故障处理”等清楚标题；外部链接注明来源和联网需求。外部手册的版本或地址未经核实，不称为最新官方文档。内网无法访问 GitHub 时，可将同一 Markdown 文档集发布到企业文档站，再统一调整检索来源链接；当前尚未配置内网文档站。

## 发布检查

1. 修改代码时同步更新主文档，尤其认证、默认目录、响应结构和错误提示。
2. 执行 `python3 scripts/check_docs.py` 检查维护文档的本地链接、图片与公开接口覆盖。此检查不验证远程链接或字段语义，后者仍需评审。
3. 执行 `sh tests/run.sh`，真实 DSH 环境额外运行 `node tests/runtime-account.cjs`；缺少运行时则在对应容器内执行，不能把未执行写成通过。
4. 发布前备份 PHP/DSH 插件与实例配置，按 [部署说明](deployment.md) 同步两端及 docs/kod。重启 DSH 清除手册缓存，保留凭证、会话和网盘数据。
5. 在测试账号核对个人/企业空间、子目录、问题标题、文件卡片及预览、过期凭证新建对话和帮助来源链接。
6. 记录镜像版本、Git 提交、验证结果及回滚点后提交推送。截图含私密内容或日志包含 token 时不要提交。
